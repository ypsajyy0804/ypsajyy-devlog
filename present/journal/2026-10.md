### ① `malloc` 出来的字段看着是 0，其实不是他写的（10-17 / 10-18 连续两次）

```
现象：  双向链表 B05.c 打印全对，但 p1->prev 从未赋值，gdb 里显示 0x0；
        10-18 单链表 B06.c 第 7 组同理，head->next 没赋值，erase(head,0) 却"正确"返回 NULL
工具：  gdb 的 p p1->prev / p *(p1->prev)；printf("%p")；free→malloc 复用实验
根因：  malloc 只给你一块字节，不给你一个"节点"。第一次分配通常拿到内核刚清零的新页，
        所以看起来是 0 —— 那是内核为了不让进程读到上一个进程的数据而做的，不是代码写的。
        一旦这块内存被 free 过再分配，开头 16 字节会被 glibc 的 tcache 写成 next/key 指针，
        其余位置留着上一个用户的旧数据。
        实测（10-18）：free 后重新 malloc 同样 100 个 int，同一程序跑三次打印
        -128685088 / -726910426 / -739369745，三次都不同 —— 那是随机化后的地址低 32 位。
修复：  新建节点时 val 和 next 一次写完，一个都不留；10-18 补 head->next = NULL;
```

### ② `%d` 打 `size_t`，打印出 705032704（10-15 / 10-18 复现）

```
现象：  printf("%d\n", (size_t)5000000000) 输出 705032704
工具：  gcc -Wall -Wextra -Werror 的 -Wformat 报错；gdb 里逐行 next 观察
根因：  (size_t)5000000000 = 0x12A05F200，是 8 字节；%d 只读低 4 字节 0x2A05F200
        = 705032704。这不是"截断成 int"那么简单 —— 是 printf 按 %d 的格式去读 4 字节，
        剩下的高位根本没被读，属于未定义行为的一种。
修复：  size_t 一律用 %zu（LP64 上 size_t 就是 unsigned long）
```

### ③ `printf(n)`：把 `int` 当格式串传进去（10-21）

```
现象：  int n = printf("hello");   // n = 5
        printf(n);                 // ← 想打印 n，实际传的是整数
工具：  gcc -Wall -Wextra -Werror（这一行编译不过）
根因：  printf 的第一个参数类型是 const char *（格式串地址），n 是 int（值是 5）。
        编译器会做指针←整数的隐式转换，并警告
        "passing argument 1 of 'printf' makes pointer from integer without a cast"；
        运行期它会把地址 0x5 当字符串去读 → 段错误。
修复：  printf("%d\n", n);
```

> 这一条的价值不在修复本身 —— 是提醒：**报错信息 gcc 早就给了，问题是有没有去看。**
> 他写这段时没有编译过，所以那两行是"推演"出来的结果。
