## 这是什么

**这是目前最偏离传统 Web 的一个项目**，也是我自己最想做的。

目标不是做一个聊天界面，也不是给图片加抖动效果，而是：

> 聊天过程中，系统根据**话题**生成相关的画面，并让画面**持续运动**下去。

比如说，聊到下雨，画面里就应该有雨，而且是**一直在下的雨**，不是一张静态的雨图。

## 项目的结构

已经搭起来的部分：

- **Python 服务** —— 后端逻辑
- **LLM 对话导演** —— 把聊天内容转成「该画什么」的指令
- **分镜绘制与画面合成** —— 指令 → 具体画面
- **`tuikit`** —— 渲染工具
- **离线预览** —— 不接 AI 也能看画面

## 问题的四层

这个项目看着是一个东西，其实是四个不同的问题叠在一起。**分开看才知道自己卡在哪一层。**

| 层次 | 问题 | 我现在的状态 |
|---|---|---|
| 一 | **理解对话** —— 把话题转成机器能执行的场景描述 | 能跑，靠 LLM |
| 二 | **生成画面** —— 场景描述 → 颜色 / 图形 / 文字 / 布局 | 能跑 |
| 三 | **让画面持续运动** —— 随时间变化产生动画，而不是每帧重画静态图 | ⚠️ 机制不清楚 |
| 四 | **实时运行** —— 控制帧率、延迟、绘制成本、状态更新 | ⚠️ 性能瓶颈在哪不知道 |

之前测到过约 **165ms/帧、约 8 FPS**。这组数字只代表当时的实现状态，不代表项目最终效果——但它说明**第四层是真问题**。

## 计划走的路

讨论过的路径：

```
现有 Python 架构保留
      ↓
先学浏览器端 JavaScript + Canvas 2D + requestAnimationFrame
      ↓
建立「实时动画 + JSON 场景状态」
      ↓
再接入 AI
      ↓
WebGL / WebGPU 暂时后置
```

理由：先把**动画和绘制机制**弄懂，再理解场景状态怎么更新，最后才是性能优化和更高级的渲染。
