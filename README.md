## 这个仓库是什么

我大三上开学时做了一次盘点，结论不太好看：

**我的项目经验，领先于我对程序的理解。**

大学前两年我靠 AI 编程工具做出过几个完整的 Spring Boot + Vue 项目，也在小公司实习交付过系统。但那些代码是 agent 生成的——pom 和 yaml 我看得懂，三层架构的业务逻辑和各种接口我读不明白。换句话说：**我能让软件跑起来，但我解释不了它为什么能跑。**

我不想继续堆叠第 N 个增删改查系统。这个仓库是我换路线的全部记录：**当前能力自评 → 48 周路线图 → 每周进度 → 练习代码 → 踩坑日志**，全都摊开写。

## 关于 AI 的使用

我不打算假装不用 AI——那是自欺欺人，2026 年没人这么干活。

但我给它写了一份 [`CLAUDE.md`](CLAUDE.md)，核心是一条：**默认模式是教学，不是交付。** 我贴代码求助时，它必须从「先跑一遍、你自己怀疑哪一行」开始，一次只降一级提示，不许直接给我修好的代码。只有环境配置和纯 API 签名这类记忆性内容才允许直接回答。

原因写在那份文件最后一句：

> 我的目标不是「跑通」，是面试的时候能从内存/内核层面讲清楚每一行。
> 如果某个做法能让我明天就交差、但让我少学一个机制 —— 不要给我。宁可让我多花三天。

## 自检标准

我不再用「我会不会 Spring Boot」这种问题评价自己。改用这 6 条（见 [`docs/self-assessment.md`](docs/self-assessment.md)）：

- [ ] **独立编程** —— 不复制 AI 生成的完整代码，独立写出一个小功能，并解释每个关键步骤
- [ ] **阅读代码** —— 从一个入口开始，追踪请求、数据处理、返回结果的完整过程
- [ ] **调试能力** —— 遇到异常时，能通过日志、断点、最小复现逐步定位原因
- [ ] **原理解释** —— 不背术语，能用自己的话解释程序为什么这样运行
- [ ] **系统设计** —— 能说清模块职责、数据如何流动、为什么选某个方案
- [ ] **性能判断** —— 能区分功能正确 / 运行流畅 / 资源合理，并通过测量而非猜测优化

只有在具体任务里验证过才勾选。**不确定就留空——留空比自我感觉良好有用。**
