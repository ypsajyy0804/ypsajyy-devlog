## 这是什么

这不是一份学习计划。计划只是它的一部分。

我大三上开学时做了一次盘点，结论是：**我的项目经验，领先于我对程序的理解。** 前两年我靠 AI 做出了几个完整项目，也实习交付过系统，但那些代码是生成出来的——我能让软件跑起来，解释不了它为什么能跑。

所以我换了一条路：从 Web 应用走向系统底层。这个仓库记录这条路的**全部三段**：

| | | |
|---|---|---|
| **[过去](past/)** | 我做过什么 | 项目复盘、踩过的坑、折腾过的东西，以及**每个项目留下的未解问题** |
| **[现在](present/)** | 我正在做什么 | 每周进度、每日题目、手写代码、笔记、月度日志 |
| **[未来](future/)** | 我要去哪 | 48 周路线图、目标岗位、检查点 |

**组织规则只有一条**：根目录只放 `README.md` 和 `CLAUDE.md`，其余一切都归属 `past/` `present/` `future/` 之一。

## 关于 AI 的使用

我不打算假装不用——那是自欺欺人。但我给它写了份 [`CLAUDE.md`](CLAUDE.md)，核心一条：**默认模式是教学，不是交付。** 我贴代码求助时，它必须从「先跑一遍、你自己怀疑哪一行」开始，一次只降一级提示，不许直接给我修好的代码。

原因写在最后一句：

> 我的目标不是「跑通」，是面试时能从内存/内核层面讲清楚每一行。
> 如果某个做法能让我明天就交差、但让我少学一个机制 —— **不要给我**。宁可让我多花三天。

## 我怎么判断自己有没有进步

不用「我会不会 Spring Boot」这种问题。用这 6 条，**只有在具体任务里验证过才勾**：

- [ ] **独立编程** —— 不复制 AI 生成的代码，独立写出一个小功能，并解释每个关键步骤
- [ ] **阅读代码** —— 从一个入口开始，追踪请求、数据处理、返回结果的完整过程
- [ ] **调试能力** —— 遇到异常时，能通过日志、断点、最小复现逐步定位原因
- [ ] **原理解释** —— 不背术语，能用自己的话解释程序为什么这样运行
- [ ] **系统设计** —— 能说清模块职责、数据如何流动、为什么选某个方案
- [ ] **性能判断** —— 能区分功能正确 / 运行流畅 / 资源合理，并通过测量而非猜测优化

**留空比自我感觉良好有用。**
